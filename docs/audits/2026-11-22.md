# Hermit 整体复查与页面审计（2026-11-22）

基线：`main` 的 `3738f91`。日期为北京时间。上一轮见 [2026-11-12 代码复核](2026-11-12.md)，那里已修的项本轮没有复现，不再重复。

范围：

- 后端：Crab 网关与控制台鉴权、`Invoker`（授权、快照、确认、幂等、文件入参）、文件暂存区、调用记录、API Key、同步与版本留存、定时清理；Reef 的发布、分发清单、目录查询。
- 页面：Reef 管理端 11 个路由、Crab 控制台 12 个路由，各自在 1440×900 和 390×844、浅色和暗色下用真实 Chrome 打开，共 92 张截图，同时收集控制台报错和页面级横向溢出。
- 基线测试：全量 `verify` 与前端 `typecheck`、`npm test`。

本次不是渗透测试，没有做依赖 CVE 扫描、生产压测和 MySQL 上的实测（见「没有验证的部分」）。

## 发现与修复

| # | 类别 | 问题 | 证据 | 修复 |
| --- | --- | --- | --- | --- |
| 1 | 性能 | Reef 分发清单每次轮询都读出所有规则包的所有版本（含 `validation_json`、`diff_json`），并对每个当前包重新验签、解析 YAML，结果是 304 时也一样。每台 Crab 默认 5 分钟轮询一次 | 代码路径：`ConchDistributionService.manifest` → `repository.listAll()` + `verifier.verify` | 只查 `is_current` 的行。清单条目按 zip 的 SHA-256 缓存：每次仍然读文件、算摘要，摘要没变才复用，磁盘上的包被改动会重新验签并返回 500。`ConchApiTest.manifestNoticesAPackageChangedOnDiskAfterAnEarlierPoll` |
| 2 | 性能 | Reef 查一个规则包的版本、查一个已发布版本，都是读全表再在内存里过滤 | 代码路径：`ConchCatalogService.rowsOf`、`ConchDistributionService.publishedRow` | `ConchRepository` 增加 `listByConch`、`find`，条件下推到 SQL。行为不变，现有用例覆盖 |
| 3 | 并发 | Crab 记录「某版本最近一次成功」是先 UPDATE、没改到再 INSERT。一个版本的头两次成功并发时都走到 INSERT，后一个撞主键，异常被 `Invoker` 接住只打一行告警 | 代码路径：`SyncStore.recordSuccess` | 改成一条 `MERGE ... KEY (conch, version)`。`VersionSuccessTest.concurrentFirstSuccessesLeaveOneRowAndNoError`（16 个线程、20 轮） |
| 4 | 性能 | 正式规则包每次调用成功都开一个事务写 `version_success`，这个时间只用来决定留存哪个旧版本 | 代码路径：`Invoker.publish` | 同一个版本 60 秒内只写一次；换版本立刻写，所以「最近成功的是哪个版本」不受影响。节流状态在内存里，重启后第一次成功照常写。`VersionSuccessTest.repeatedSuccessOfOneVersionWritesAtMostOncePerInterval` |
| 5 | 页面 | 服务停了或网络断开时，两个前端直接弹出浏览器原文 `Failed to fetch` | 代码路径：`shared/http.ts` 四处 `fetch` 没有接住拒绝 | 统一抛 `NetworkError`，文案「连不上服务：服务可能已停止，或者网络断开…」。它不是 `ApiError`，不会触发登录失效处理。`http-network.test.ts` |
| 6 | 页面 | 390 px 宽时，Crab「可订阅规则包」和 Reef「用户管理」的操作列固定在右侧，宽 200 px / 160 px，盖住大半张表：规则包标题和说明被截断，用户表只看得到一列 | 真实 Chrome 截图 | 窄屏（≤640 px）不固定这两列，横向滑动查看；用户管理补上已有的滑动提示。修复后重新截图确认 |
| 7 | 测试 | `LegacyTransportTest.localhostRefusedNamesBothPeers` 写死要求出现 `::1`。`localhost` 只解析到 `127.0.0.1` 的机器上基线就失败 | 基线 `verify` 失败；`getent ahosts localhost` 只有 IPv4 | 按本机实际解析结果断言，每个对端都要出现 |
| 8 | 测试 | `CliTest.lockedDatabaseExitsWithTheConsoleHint` 起子进程比对完整输出。环境里有 `JDK_JAVA_OPTIONS` 时 JVM 自己打一行 `NOTE: Picked up ...`，用例失败 | 基线 `verify` 失败 | 子进程环境去掉 `JDK_JAVA_OPTIONS`、`JAVA_TOOL_OPTIONS` |

第 7、8 项只改测试，产品行为没有变。

## 复查过、没有发现问题的部分

- `CrabHttpServer` 的控制台访问检查（回环、`Host`/`Origin`、`X-Hermit-Console`、会话）。

- 页面：92 张截图没有控制台报错，没有页面级横向溢出；浅色和暗色的对比度、空状态、侧栏抽屉、未知路由页表现一致。

## 记下来、本轮没有改的

| 项 | 说明 |
| --- | --- |
| 幂等缓存包含瞬时失败 | 带幂等键的 POST，上游超时或 `UPSTREAM_ERROR` 的结果也会在有效期内原样重放（只有 `LOGIN_INPUT_REQUIRED` 不存）。这符合「同一个键同一个结果」，但调用方用同一个键重试瞬时失败时拿不到新结果。要不要排除瞬时错误是产品取舍，没有改 |
| 清单仍然每次读全部当前包 | 第 1 项省掉的是验签、解析和多余的行；读文件和算摘要保留，用来发现磁盘上的改动。规则包数量很大时可以再换成按文件修改时间判断，代价是放弃这层检查 |
| 文件暂存区的个数上限 | 检查和登记不是一个原子步骤，并发上传可能略微超过个数上限；总容量是预留的，不会超 |
| 前端请求没有超时 | 服务挂住不回时页面一直转圈。加统一超时会影响长时间的试跑和上传，需要按接口区分 |
| 概览页「同步状态」卡片 | 和右侧「开发者模式」等高，内容少时下半部分是空的 |

## 追加：规则执行引擎复查

范围是 Crab 的 `RuleEngine`、`StepRunner`、`HttpCalls`、`SessionManager`、`Extractors`、`ScriptStep` 和 common 的模板。没有发现会让结果出错的缺陷。下面 6 项只减少重复工作，规则语法、返回值、错误句子和打码范围都不变。

| # | 位置 | 原来 | 现在 |
| --- | --- | --- | --- |
| E1 | `SessionManager.persist` | 每次上游交换之后都把 Cookie 序列化、加密、开事务写库，Cookie 没变也写 | 和上一次写进库的内容相同就跳过。进程启动后的第一次、作废会话之后、写库失败之后仍然照常写 |
| E2 | `Extractors` | 一个 `extract` 步骤有 N 个字段就把正文解析 N 遍；jsonpath 每个字段解析两遍；`each` 里每行每字段重新解析，xpath 每次新建 `XPathFactory` | 同一步骤里相同的文本只解析一次（HTML、W3C DOM、JSON），`each` 的每一行在各字段之间复用；工厂每个线程留一个。会就地改解析结果的表达式不读共用的那一份：带括号的 jsonpath（`append()` 等函数）和 css 的 `:matchText` 仍然各自重新解析 |
| E3 | `ScriptStep` | 每次调用重新解析脚本库、`code` 和内置的 `hermit` 前置脚本 | 按源码缓存解释模式的编译结果，最多 64 条、源码合计 16 MB。标准对象仍然每次新建，沙箱不变；编译失败不缓存；含反引号的源码不缓存，因为带标签的模板字面量会把第一次调用的数组记在编译结果上 |
| E4 | 模板 `Expressions.parse` | 每次渲染、每次找 `login.*` 和凭证引用都重新解析模板串 | 含 `{{` 且不超过 8192 个字符的模板按原文缓存解析结果，最多 4096 条，满了清空；解析失败不缓存 |
| E5 | `RuleEngine.finish` | 每次调用构建两次打码器，各自把所有秘密按 4 种字符集展开 | 没有开发追踪要落库时只构建一次 |
| E6 | 账号连接池 | 空闲连接一直留到账号被删除 | 每分钟关掉闲置超过 1 分钟的连接和已过期的连接，不动 Cookie、登录状态和账号锁 |

记下来、没有改的：

| 项 | 说明 |
| --- | --- |
| 同一账号的调用串行 | 账号锁从开始拿到结束，等锁时间算进能力超时。这是保护会话 Cookie 的设计，改了会改变现有行为 |
| 账号状态不回收 | 每个 `(origin, conch, account)` 的锁、Cookie 罐和客户端对象留到账号被删除。E6 之后空闲时不再占连接；对象本身留着，因为里面有连续登录失败次数和暂停标记，丢掉会改变行为 |
| 下载整份进内存 | `download` 的正文先全部读进内存再写暂存区，单文件上限默认 50 MiB。改成边读边写要重排超时、截断和失败清理，本轮没有动 |
| 登录引用没有按规则包缓存 | 每次调用仍会遍历步骤找 `login.*` 和凭证引用；E4 之后这一步只剩遍历，不再解析 |

验证：`EngineReuseTest`（提取、脚本）、`SessionManagerTest`（Cookie 写库、空闲连接）、`TemplateEngineTest`（模板缓存）。`EngineReuseTest` 的提取用例在改动前的 `Extractors` 上同样通过。没有做压测，收益没有量化。
